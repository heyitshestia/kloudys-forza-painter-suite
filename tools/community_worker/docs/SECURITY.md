# Security Model

## Separation

The community service has no access to supporter keys, activation receipts,
source images, generator reports, KFPS settings, or game memory. The desktop
client uses a separate `/v1` endpoint and stores only its community session under
`runtime/community`.

Supporter verification crosses that boundary only as a 15-minute RSA-signed
entitlement. The activation Worker binds an opaque entitlement ID to the requested
Community user ID and signs the audience, subject, nonce, and times. The Community
Worker receives no supporter key, key proof, activation receipt, purchaser identity,
device ID, Windows identity, or local path.

## Identity And Sessions

- Production identity is verified through GitHub OAuth Device Flow.
- GitHub access tokens are checked once, then discarded.
- Community bearer tokens contain 256 random bits and are stored only as SHA-256
  hashes in D1.
- The desktop copy is protected with Windows DPAPI for the current Windows user.
- Sessions expire after 90 days, a user may retain at most eight sessions, and
  sign-out or suspension revokes server-side sessions.
- Usernames are unique without regard to case and an SQLite trigger makes them
  immutable after the first successful claim.
- Username claims require a second exact, case-sensitive confirmation value before
  availability checks and the immutable database update.
- Supporter entitlements are canonical, signature checked, audience bound, request
  bound, account bound, rate limited, and rejected after expiry. A single opaque
  entitlement ID cannot be attached to two Community accounts.

## Untrusted Uploads

- Request bodies, fields, lists, nesting, shape counts, numeric ranges, JSON size,
  and preview size are bounded before storage.
- Uploaded JSON is rebuilt into a canonical allowlisted schema. Unknown metadata,
  local paths, and non-rendering score fields are discarded.
- Game origins and schema labels are derived from the design. Client-provided game
  labels are ignored, and unrecognized explicit schemas require a separate warning
  acknowledgement before publication.
- PNG signatures, dimensions, encoding fields, chunk boundaries, critical chunks,
  CRCs, IDAT presence, and IEND placement are checked.
- Full previews and compact thumbnails have separate byte, dimension, and
  content-hash limits. Catalog cards do not decode the full inspection preview.
- Semantic design hashes and preview hashes are checked across revision history;
  a D1 unique index also closes simultaneous preview-upload races.
- R2 keys are generated by the service and never accepted from clients.
- Public catalog queries always exclude supporter-only rows. Restricted list,
  search, detail, preview, thumbnail, and download paths all recheck current
  entitlement server-side and use private no-store responses.
- Database publication happens only after all three R2 objects are written; failed
  database operations remove their uniquely named staged objects.

## Abuse Controls

- D1 rate limits cover authentication, username claims, profile updates, uploads,
  revisions, reports, favorites, and follows.
- New artwork uploads allow 50 submission attempts per account in each fixed
  30-minute window. Revision and other action limits remain separate.
- Favorites and follows have database uniqueness constraints.
- Downloads require an authenticated Community session. Popularity counts at most
  once per user, artwork, and UTC day.
- Structurally valid production uploads and revisions may publish immediately when
  `AUTO_PUBLISH_VALIDATED_UPLOADS` is enabled. Validation does not make subjective
  copyright, artwork, or game-policy decisions.
- Reports, removals, approvals, rejections, features, and suspensions create or
  retain audit records.
- The desktop client never places supporter-only metadata or previews in its public
  disk catalog cache. Restricted previews are fetched with the Community session,
  hash checked, and retained in memory for the current process only.

## Administration

The included `/admin` console is intended for one trusted operator. It requires a
high-entropy secret header, keeps the token in browser session storage, escapes
catalog content before inserting it into HTML, and is served with a restrictive
Content Security Policy. Browser API access is limited to the Worker's own origin;
the desktop client does not rely on CORS. Use a separate Cloudflare secret and
never put the token in source control.

The VERSION floor is fetched only from the configured official GitHub repository.
The Worker resolves the branch to a commit first, then reads `VERSION` at that exact
commit. Upload-provided versions can trigger a rate-limited refresh but can never
set the floor. Failed or older responses retain the prior floor; lowering it requires
an authenticated admin action.

Before delegating moderation to multiple people, replace the shared token with
short-lived named administrator sessions and role-based permissions.

## Production Checklist

1. Keep `ALLOW_TEST_AUTH` and `AUTO_APPROVE_TEST_UPLOADS` set to `0`; explicitly
   choose whether `AUTO_PUBLISH_VALIDATED_UPLOADS` is `1` or `0`.
2. Use a dedicated D1 database, private R2 bucket, Worker, and admin secret.
3. Set a real GitHub OAuth client ID with Device Flow enabled.
4. Apply every remote migration before deploying code that depends on it.
5. Configure Cloudflare request limits and alerts around upload and admin routes.
6. Export D1 metadata and test restoration into staging.
7. Review highlighted reports regularly and remove confirmed policy violations.
8. Verify the supporter public key ID/modulus matches the separately deployed
   activation Worker before enabling the Supporters scope.
9. Confirm scheduled VERSION synchronization, manual pause, and explicit rollback
   in staging before relying on it for release enforcement.
